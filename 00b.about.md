In this book, you will learn to solve problems in physics using computational tools by programming these problems into a computer.

## Why are programming and computational tools important in physics?

One reason is that while many of the (toy) problems you will encounter in your undergraduate program have analytical solutions (since they are chosen carefully by the teachers of your course), most problems encountered in physics will in general not have an analytical answer, and so if you really need to know the solutions of these non-simplified problems, you will have to calculate them numerically.

Another useful reason is that computational solutions to problems can often provide quick insight into complex equations without too much work: once you know how to program the numerical solution, you can use your computer to do numerical "experiments", playing with parameters to explore what happens.

And finally, programming itself has become an essential toolbox for the physicist: from programming the control and acquisition of data in experiments; to the processing, plotting, and analysis of data from experiments; to plotting and analysing theoretically derived formulas, to numerical computations for simulating complex problems in physics; and the list goes on.
A high proficiency in programming is now considered an essential skill in physics, and is one that is also highly valuable for careers outside of physics.

## Python

The programming language we will use is Python, one of the most popular programming languages right now, and one which has come to dominate the physical sciences.
It has become popular because of its flexibility and simple syntax.
Although it is slower than some of the traditional low-level languages like C or Fortran, this has become less of an issue for many problems as computers have gotten faster, and for heavier numerical calculations, it can easily interface to libraries that run highly optimized code
pre-compiled in low-level languages.

### Marimo islands

The code cells in this book are [marimo](https://marimo.io) cells, and they behave a little differently from a classic Jupyter notebook.
The difference is worth understanding up front, because it will save you confusion later.

A Jupyter notebook runs cells in whatever order you evaluate them, and remembers everything you have ever run — including variables from cells you have since deleted or changed.
That is a common source of errors and non-reproducible results.

[marimo](https://marimo.io/) instead works out the *dependencies* between cells and keeps them consistent.
If you change `x` in one cell, every cell that uses `x` updates automatically.
There is no hidden state, and no "restart and run all" needed to be sure of your results.

:::{important} One cell owns each variable

That guarantee comes with one rule:

A variable can only be assigned in **one** cell. 
If two cells both did `x = ...`, marimo would have no way of knowing which value the rest of the notebook should see, so it refuses to run.
:::

Three consequences for the exercises here:

- **Re-assigning a name in a later exercise will error.**
  If you want a scratch variable that is private to one cell, start its name with an underscore — `_tmp`, `_i`.
  Underscore names are local to their cell, so you can reuse them freely.
- **Some variables are numbered.**
  You might see suffixed variables `t_2` or `h_3`.
  That is what keeps each exercise's version of common variables like `t` distinct.
  In general, it's good practice to use descriptive variable names.
- **The reference solutions have their own copies**, suffixed `_sol1`, `_sol2` and so on, so that opening a solution never overwrites the work you have done.

:::{tip} Running a cell
Press the run button on the cell.
Cells that depend on it re-run by themselves.
:::

:::{warning} Leave the last line of an exercise cell alone
Each exercise cell ends with a line like `show(x=x, y=y)`.
That line is what the cell *displays*, and a cell that displays nothing has no run button — so if you delete it and run the cell, you will not be able to run that cell again..
If it happens, reload the page; your other work in the page is lost, so it is worth avoiding.
:::

Because every cell runs as soon as the page loads, a cell whose exercise you have not done yet would otherwise run on values that do not exist.
So exercises start like this:

```python
# Fill these in as you work through the exercise.
y = yt = None

# y = .....
# yt = .....

if given(y, yt):
    ...the code that plots or prints your answer...

show(y=y, yt=yt)
```

`None` means "not filled in yet", and `given(...)` is true once every blank it names has a real value.
Until then the `if` is false, the cell quietly does nothing, and it tells you what it is **waiting for**.

Two things follow from this that are worth knowing:

- **Write your answer where the commented hints are** — above the `if` statement.
  Code written *inside* the `if` block cannot switch the `if` on.
- **A cell may be waiting for an earlier exercise, not this one.**
  Chapters build on themselves:
  if Fourier Transforms I exercise 1 defines `t` and `fs`, then most of that chapter waits on it.
  Fill in exercise 1 and the rest of the chapter comes to life at once, without you running anything — which is the reactive model described above, in action.

Where an exercise asks you to write a *function*, the same idea applies to its body:

```python
def f(x):
    return None
```

`given(f)` counts a function as filled in once you have replaced that `return None` with the real thing, so functions and values read the same way.

A few exercises ask you to complete a loop that cannot run until you do — it would spin forever, or quietly produce an answer from an array you have not filled.
Those carry a switch you turn off yourself when you are done:

```python
# Set `_unfinished` to False once you have completed the loop below, so that it can run.
_unfinished = True
```

## This book

This book offers an interactive environment for you to learn about, and implement, the algorithms you will most often need to solve or quickly benchmark a physics problem.

The code cells you see are **live and editable**, and they run entirely inside your own browser — there is no server, and nothing to install.

:::{important} Your work is not saved
Editing and running code here does not save your progress.
If you want to keep your work, copy it somewhere safe before you close the tab.
:::

Each exercise is followed by a check that compares your result against the expected answer and tells you what does not match.
You do not have to ask for it: because the cells are reactive, the check re-runs itself the moment you change your answer.
The solutions are provided alongside the questions, collapsed behind a **Solution** dropdown, so you can look at them at any time if you get stuck.
Please try to solve the problem yourself first, and use the answer check to get feedback, *before* resorting to the solution.

### A note on using AI

Every exercise in this book can be solved in seconds by an AI assistant.
We are not going to pretend otherwise, and we are not going to try to stop you.

What we will say is this: the point of these exercises is not the answer, it is the ability to produce the answer.
That ability is what the exam tests, and more importantly it is what you will need the first time you meet a problem nobody has solved for you.
Watching someone else — human or machine — write the code builds it very slowly.
Writing it yourself, getting it wrong, and working out why builds it quickly.

So: try each exercise yourself first, and use the answer check to find out where you stand.

Where an AI assistant genuinely helps is *after* that.
If you have looked at a solution and a line of it makes no sense, asking an assistant to explain that line — what the function does, why the indices are what they are, what would break if you changed it — is an excellent way to learn.
